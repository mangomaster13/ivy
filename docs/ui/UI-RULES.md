# UI rules · confirmed 2026-09-19

Current gameplay and document precedence: [IVY-GUIDE.md](../gameplay/IVY-GUIDE.md). Engineering and save compatibility: [DEVELOPMENT.md](../engineering/DEVELOPMENT.md). This file owns concrete UI rules and testing policy; earlier plans and art notes do not override it.

## Design previews must match the project

For new or redesigned gameplay artwork, the user requires a concrete visual design proposal before development (2026-09-20). Wait for approval of that proposal, then implement it directly without another design-approval loop. Do not substitute plain filled rectangles, rounded cards or colour blocks for designed physical objects such as menus, clipboards or neon signs. Give them authored silhouettes, materials, texture and physical detail. This does not prohibit actual colour within the illustration or require redesigning unrelated shared controls.

All future design images, concept art and UI mockups must match Yard's scene art style as defined in [the image generation rules](../art/IMAGE-GENERATION-RULES.md), including the game's actual controls. Before making a preview, inspect the Yard art anchors, current game screenshots and the relevant shared components/assets. Reuse their button shapes, surfaces, colors, typography, icons, proportions and states; in particular, match the existing PuzzleButton and Back controls rather than inventing approximate replacements. Use existing controls directly in composed previews where possible. A concept image is not an exception to the project's UI rules. Preserve the established painting style, palette and visual hierarchy unless the user explicitly requests a redesign.

For all generated or edited scene/object artwork, follow [the image generation rules](../art/IMAGE-GENERATION-RULES.md): consistent perspective, believable furniture scale, physical support and spatial circulation are mandatory even in the storybook style.

## User photographs require recreated artwork

When the user supplies a photograph as a visual reference for a scene, object, sign, ingredient or product, recreate the relevant visual as authored game artwork in Ivy’s approved style. Preserve recognizable shape, proportions, materials and identifying details. A text label, description, generic icon or generic object with a renamed caption is not a substitute for the referenced asset. Do not simply paste the original photograph into the game unless explicitly requested. Native text may supplement the recreated artwork for legibility and interaction, but cannot replace it. Inspect the supplied reference first, then present the required visual design for approval before implementing new/revised artwork; retain the source and provenance and derive exports from the approved high-resolution original. A photo supplied solely as a bug screenshot remains diagnostic evidence, not an automatic request to recreate the entire screen.

## Text artwork and Notes — user revision 2026-09-20

Outside Notes, interactive lock-pad text and the player's live handwriting in Dictionary, visible lettering must be designed artwork, not ad hoc native text over an illustration. This includes physical recipe books, signs, product labels, perfume-box inscriptions and Dictionary's printed lyric card. Notes and lock pads retain native interactive text; Dictionary's written strokes are drawn and saved from the player's input, not preprinted as completion art. This revision supersedes earlier requirements for native display lettering outside those exceptions; preserve approved wording, type style, interaction and accessibility semantics when changing its rendering.

Design lettering within the actual writable surface, with margins for borders, folds, spine and perspective. Deliver it in the approved object artwork or as a designed transparent lettering asset sharing the object's coordinates and transform. Do not substitute a plain text overlay, clip overflow, truncate names or use tiny type. New/revised artwork follows the existing design-preview approval workflow. Notes text still obeys physical page bounds. Notes and scene backgrounds cover the full root-owned content viewport without stretching physical artwork.

In Tools, pin the Notes entry at the leading/first position outside the horizontally scrolling tool list. Only the remaining tools scroll; Notes stays visible and stationary regardless of inventory length or scroll position. Keep it in the footer, not over content.

Every Notes opening resumes the last reading location, including after leaving a scene or restoring the app. Remember the logical page/clue identity rather than only a transient numeric index: discovering new clues must not shift the reader to unrelated content. First use opens the first page; if the remembered page is unavailable, fall back to an available page without resetting other progress. Preserve return to the originating scene/closeup.

These are requirements for subsequent implementation, not a claim that the current app already satisfies them.

## Composition

`story-lock-panel` is reserved for explicit answer-entry or abstract puzzle interfaces, such as the mailbox, door, room-code pad and route selection. It is not a universal inspection background. Ordinary reading of a ticket, inspecting a keepsake, opening a container and collecting its contents must use the scene's own full-screen artwork. The shared inspection shell requires an explicit surface choice; it must never default to the lock panel.

Container closeups show their physical contents directly, without a page title, permanent instructional plaque or tool-selection strip. Players select or drag tools from the footer; do not add a duplicate answer-tool button inside the closeup. After opening, retain Back and clickable contents. Narrative reactions and non-instructional failure feedback may appear; do not tell the player the required operation.

Main puzzle feedback follows the [anti-greedy gameplay rule](../gameplay/IVY-GUIDE.md#防穷举完成规则--2026-09-23): do not reveal a correct prefix, correct item, or correct drawer after each low-cost tap. Show physical consequences of experimentation and judge a meaningful complete operation. Short collection interactions are allowed; attempt limits and tool loss are not substitutes for inference.

Picking up any tool automatically switches the footer to Tools (2026-09-20 revision), including menu books, ingredients, finished perfume bottles and Rose petals. It does not auto-select/use the item or start a separate tool showcase. Save restoration and migration are not pickups and must not force a tab change. Memories / Tools remain freely switchable during puzzles. A selected tool's actual manipulation response is distinct from an unsolicited tool recommendation. Consumed tools and placed petals leave no empty tool slots; the thirteen Memories slots retain their stable identities.

Collecting any new keepsake automatically switches the footer to Memories at ownership commit, including physical pickups, assembly completion and direct Element rewards. Do not depend on a collection flight to trigger this switch. Reopening an owned keepsake, restoring saves and migrating progress must not force a tab change.


**No pasted-image design.** Never place a rectangular scene illustration, screenshot, or baked interface inside another decorative panel. A closeup is a complete spatial scene: its artwork fills the scene stage, with interactive objects and controls positioned intentionally within it. Do not hide a pasted rectangle with rounded corners, fades, shadows, or a decorative border.

Transparent object sprites may represent actual independent game objects; they must share the scene's perspective, scale, light and illustration style. A photograph, ticket or letter may appear as a physical object when it is the object the player is inspecting, not as a substitute for layout. UI text and controls stay native and independently interactive.

Use Yard's matte pixel-storybook painting style as specified in the image generation rules. Preserve reference objects' silhouettes. Export all device scales directly from the high-resolution original, never from a low-resolution catalog image. Device rendering acceptance follows the testing policy below.

## Physical object alignment

For objects placed on surfaces or inside containers, follow the [object–container fit specification](object-container-fit.md). Define the physical relationship, approve the assembled composition, then derive artwork, anchors, occlusion and interaction states together. Rectangle containment alone does not prove that an object is seated. This applies to recesses, boxes, drawers, trays, beds, tables and shelves.

**Container containment is mandatory (2026-09-20).** Each object belongs to a physical support/container: meals and cloths to the tabletop, Rose to the bed, menus to their board. Define the usable support bounds from the actual background artwork before placing objects. For flat objects, keep the complete footprint inside those bounds in every state, including revealed, taken, served and animated positions; checking only the centre is insufficient. For upright objects, the full supporting base must sit inside the surface; their height may naturally project above the rear edge in perspective. Never stretch furniture to contain that vertical projection. Related objects sharing a canvas does not by itself establish containment. Fit/reposition the composition without stretching artwork or clipping overflow to conceal a placement error. Preserve believable furniture dimensions and the approved camera perspective. The user-selected shorter Big Top table is authoritative; the elongated v3 table is rejected. Reuse the same placement definitions for hotspots and record the owning surface beside them.


Use the `ios-design` composition/modifier-order guidance together with the project’s fitted scene rules. Inspect the source artwork and exported alpha bounds before changing placement. Define related objects as one assembly on a shared reference canvas; the main scene and closeup reuse that assembly at different scales. Do not independently guess their sizes/centres or squash an upright object to fake perspective. Account for rotation, aspect-fit letterboxing and transparent margins before defining hit/drop bounds. Layer covering objects above their contents; closed, revealed, taken and placed states must describe the same physical positions. Moving artwork requires moving its hit/drop target in the same change. Record the canvas and anchors beside the component. Visual/device acceptance follows the testing policy below, never assume code review proves alignment.

## Sign lettering, ingredient artwork and shelf placement

These rules apply to all scenes, including Le Labo (user correction, 2026-09-20).

1. **Fit lettering to the physical sign face.** Define the sign’s usable inscription rectangle/polygon with an inset from its border, not the whole image or screen. Lay out the full text using both available width and height, then apply the sign’s rotation/perspective to the complete composition. Include font metrics, line spacing and secondary text. A SwiftUI `frame` alone does not constrain a child’s drawing. Do not size solely from height, use unconstrained `fixedSize`, truncate the brand name, or clip overflowing letters. Choose a readable type size and layout before placement; if the design cannot hold the text, revise the design. Keep LE LABO and its secondary line inside the authored face in each view.

2. **Give every collectible ingredient an authored visual identity.** Before implementation, map every ingredient ID to its approved source artwork and export. A shared rendering component is fine; one generic bottle repeated with a different caption is not finished ingredient art. Differentiate ingredients through designed contents, material cues, silhouettes, closures and physical labels—not colour alone. Wood, moss, citrus, flowers, resin and powders need recognizable designed representations; abstract materials may use distinctive labelled laboratory containers. These are illustrative game representations, not claims about commercial formulas. Preserve the distinction between raw ingredients and finished perfume products. Missing artwork stays an explicit unfinished asset; never silently substitute the generic finished-perfume bottle and call the scene complete. New artwork follows the existing design-preview approval rule.

3. **Place objects by their supporting surface.** For each shelf, record the interior bounds, upper clearance and contact baseline from the actual background. Position a bottle by its visible bottom/support anchor, including alpha padding and aspect-fit offsets; its centre is not its contact point. Keep the full object inside its compartment and its base on the shelf, not floating above it or sinking through the shelf front. Keep shadows, lighting, scale and perspective consistent with the room. Do not solve alignment merely by making all objects tiny.

4. **Use stable slots, not an arbitrary screen grid.** Map each ingredient ID to a shelf/slot and an authored size/contact anchor for each camera view. Main scene, closeup, Tools and mixing slots reuse the ingredient’s visual identity; different views may need different authored perspective/placement. Derive drawing, hit targets and drop targets from the same fitted object placement. Picking up an item leaves that shelf slot empty: remaining objects must not shift because the visible array was filtered. Audit cabinet-closed, opened, partially collected and empty states. Do not draw removable objects both into the background and as sprites.

5. **Record evidence honestly.** Before delivery, review the asset map and layout definitions against the provided reference/source art. A shared component, numeric bounds or successful build is not proof that the scene visually fits. Report unresolved source/artwork needs and whether the affected rendered states were actually inspected. Runtime checks remain governed by the user-owned testing policy; these rules do not authorize automatic builds, screenshots or device launches.

## Acceptance testing — updated after ticket / Pro Max regression

Reference checklist only: execute agent checks only under the testing policy above. Simulator mentions below require a separately approved exception; routine delivery leaves manual acceptance to the user.

1. **The approved design is the baseline.** Before changing an approved surface, list its visible invariants: composition, physical object silhouette, paper/metal texture, decorative details, type roles, control grouping and enabled states. Compare final simulator screenshots against the approved mockup. A generic card is not an acceptable substitute for the designed ticket. Generated previews alone do not prove implementation fidelity.
2. **Test the user's device class.** Required layout coverage is the smallest supported landscape phone plus iPhone 17 Pro Max, not only a convenient simulator. Record device, OS, orientation and build. If that device cannot run, state the limitation; do not call the substituted device equivalent or the requested check complete.

## Lessons from the perfume playtest — 2026-09-20

- **Make the current operation legible.** Selection, carrying, placement and returning an item are distinct states. A tap must not silently change meaning because an offscreen inventory item remains selected. Show the active object/state, resolve competing selections, and give cancellation and returning to inventory distinct, consistent behavior. Preserve click/drag equivalents without adding tutorial text or revealing the answer.
- **Inventory search must not become the puzzle.** Design for the actual maximum inventory, including long names and mixtures of ingredients and finished objects. Keep persistent utilities outside scrolling content. Give item categories stable, recognizable organization; do not automatically recommend the correct tool, hide valid choices or reorder items whenever the player changes scenes. Any new grouping must preserve the existing tool-scroll restoration rule.
- **Essential controls must remain identifiable.** A navigation or mode-switch label such as Memories must not collapse to an ambiguous ellipsis. Budget the control's complete designed label/icon and hit area before distributing the remaining footer width. Do not trade readable labels or touch targets for more inventory cards.
- **Shared content needs shared placement, not just shared strings.** Notes, the physical formula book and a box inscription can carry the same information but have different physical surfaces. Reuse the semantic content and approved visual identity; each surface needs its own measured writable bounds. Apply the current text-artwork rule rather than reusing one fixed-size text view everywhere.
- **Judge the composite at playing size.** Review real-length copy, real inventory density and partially completed states in the full composition, including content, gutters and footer. An attractive background, a sharp sprite or an empty-state mockup does not prove that the assembled interface works. Distinguish interaction emphasis from scenery detail; debug RESET must not appear in release play or dominate the intended player action in review images.
- **Completion and revisiting are separate paths.** Discovery/assembly transitions explain a newly changed state. An already owned object opens its established memory directly. Preserve the player's reading and return context, and make duplicate entry idempotent. Do not replay first-time actions to compensate for a recreated view's default state.

These lessons define design requirements; the playtest screenshot alone does not prove gesture reliability, performance or every device layout. Runtime checks remain governed by the user-owned testing policy.

## One meaningful action, no redundant confirmation

A tap must carry out the action the visible element promises. If a placed menu is ready to read, tapping it opens its pages directly, not an enlarged inactive board that requires the same tap again. Placing the menu also opens its pages immediately; Back returns to the scene without a redundant board layer.

When tapping an available keepsake opens its Element presentation, commit ownership at that entry exactly once, before animation. Do not require another tap on the same object, a Collect button, or an extra reward/flight page. Big Top's served meal follows this rule: first scene tap opens Element and saves `noodle`; reopening only reads it. This does not remove meaningful discovery, tool use, or choosing separate objects from a container. Review each extra step for a distinct player decision; remove steps that merely repeat the preceding intent.
