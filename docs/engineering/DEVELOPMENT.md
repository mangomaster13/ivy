# Ivy · 代码开发原则

本文件规定后续开发的工程边界；玩法见 [IVY-GUIDE.md](../gameplay/IVY-GUIDE.md)，具体界面约束见 [UI-RULES.md](../ui/UI-RULES.md)。这些原则归纳自已完成的迭代，不要求为了符合文件而重构现有全部代码。

## 保留已成立的行为

2026-09-21 全流程反馈已明确授权对点名场景提出修改，具体范围见当前 PRODUCT 与整改 TODO；“截至 Gelato 已认可”不再阻止这些修改。本轮文件记录需求，不能作为代码已完成的证据。

新主谜题把规则判定、操作草稿、持久世界事实和奖励分开。连续手势的候选路径与多次点击不能无意共用累积提交语义；无障碍等价操作显式建模。灯管等流程先保存完成事实，再完成视觉归位、切景；动画中断后恢复事实，不把动画回调作为唯一进度来源。已完成旧存档保留收藏和通行权限。

Yard 到 Le Labo 的目标玩法以 IVY-GUIDE 的“截至香水铺的最新设计规则”为准；后四站以总纲及[后四站设计稿](../gameplay/2026-09-23-later-eggs-tool-design.md)为准。文档目标和当前运行代码分开记录。对于未被本轮点名的共享动作，修一个位置、热点或反馈时仍把改动限定在对应问题，不顺手重排解谜顺序、替换已批准物件或增加教学；遇到真实新需求时按最新要求演进。

需求已经明确或方案已获批准，就完成代码、状态与资源接入，不停留在“可以做”。用户要求先看设计稿时，先交具体稿；普通实现选择不重复索取批准。

## 状态是事实，画面是投影

沿用 GameStore 的共享状态与按玩法组织的 extension。视图负责绘制、命中与瞬态手势，核心动作由状态层判断当前位置、当前近景、前置条件和是否已完成。不能只依靠按钮 disabled 阻止非法操作。依赖工具的交互在入口检查持有状态，缺失时只显示共享 Dialog，不修改 overlay 或返回栈；已完成状态跳过已消耗工具检查，实际动作仍保留状态守卫。

把物件的 opened、picked、used／consumed 与 collectible ownership 分开。显示状态从这些事实推导，而不是借动画是否播放推断是否获得。典型约束：

- 开抽屉可以消耗钥匙，但橡皮仍等待单独拿取。
- 容器内拿走一件后，其他未取物件仍存在；再次进入不会补回已用物件。
- Gelato 整条词链与口味输入分别保存完成事实；标记字母只在词链完成后公开。输入正确不会自动选勺或发奖，主动持勺试吃后才消耗勺并领取。
- 重复触发完成事件至多发一次奖，已领取物件只播放允许的查看效果。
- 切换近景、杀进程或恢复应用，保留输入、排列、花瓣、擦拭和已发现线索；纯动画、拖拽浮层等保持瞬态。

## 存档兼容

保留十三个收藏槽的顺序及玩家已有进度。目标 ID 顺序以 [游戏总纲](../gameplay/IVY-GUIDE.md#收藏回忆与节奏) 为准：`perfume` 替换旧 `supermarket`，`dictionary` 替换旧 `sunset`。改代码时为旧收藏、房间和相关进度字段提供向后兼容的解码与迁移路径；修正局部无效字段时保留其余有效进度，不能让一个新字段导致整份旧存档作废。

维持既有迁移：旧 `ivy` 收藏归入 `letter`；橡皮继续兼容旧 pencil 标识；旧 Rose 折叠／缝合进度换算为花瓣进度，已收集 Rose 不重玩；已起飞清理 ticket 工具但保留线索。淘汰工具可以退出游戏，但旧标识仍需可解码。

普通启动恢复玩家进度。素材预览用不写正常存档的 `IVY_REVIEW`；不能为演示改动重置用户存档。需要调整 RESET 功能时，遵守最新定义：回到已解锁的 Jellycat 酒店卧室，保留前序场景工具持有／消耗、回忆、收藏、线索与擦拭事实，只重置卧室及之后内容。RESET 是显式调试操作，不是迁移或普通启动步骤；编写功能不等于获准实际执行重置。

## 容器边界与有效动作

物件放置按[物件与容器贴合规范](../ui/object-container-fit.md)建立放置契约：批准组合稿、所属表面、真实锚点、尺寸姿态、遮挡层与交互状态共用一套坐标。处于容器矩形内不等于正确嵌入；库存图标不能默认兼作场景放置素材。

每个物件先定义所属实体容器的可用范围（桌面、床面、夹板等），再安排物件落地轮廓；平放物件的完整占地、立体物件的支撑底面必须在内，不能只保证中心点在内，也不能用裁切遮掩越界。杯身等竖直部分可按真实透视高于桌面后沿，禁止因此拉长桌子或破坏家具比例。主景与近景共用坐标仍需各自核对承载面。Big Top 的主景范围与热点统一由 BigTopTableLayout 管理。

同一意图只需一次动作。已放好的菜单直接打开内容；放置成功后直接进入可操作内容，不压入无作用的中间返回层。点可领取纪念物进入 Element 的同时持久化收藏，视图不再要求第二次领取；重复进入必须幂等。仅在有独立发现或选择时保留多步交互。

主谜题接入前执行 [IVY-GUIDE 的防穷举审查](../gameplay/IVY-GUIDE.md#防穷举完成规则--2026-09-23)：写出不读线索的最短点击路径，检查状态和反馈是否构成逐位正确答案提示。只记录“读过线索”不等于已理解规则；增加选项数量或锁住尝试次数也不算修复。已完成旧档优先，短收集不强制升级为新谜题；具体待审方案见 [本轮审计](../gameplay/2026-09-23-anti-greedy-puzzles.md)。

## 一个布局所有者，一套坐标

根层唯一管理安全区、左右导航 gutter、content 和固定 footer。场景、锁板、地图、Notes、近景及反馈收到同一套可用内容尺寸，不重复扣除库存高度，不各自扩展到设备全屏。

背景、物件、热点、遮罩与手势坐标应用同一个拟合变换。320×160 是现有逻辑场景坐标，不是所有资源必须降采样到的像素尺寸。保持原图比例，并计入 aspect-fit 留白；地图经纬度使用一致比例。

从 footer 拖到内容区的物件使用统一命名／全局坐标与实际测得的目标区域。无目标的兄弟视图不能覆盖有效落点；避免库存滚动抢走拖动。归位后移除对应栏位；取消或离开时清理浮层。收集飞行动画定位真实槽位，不猜一个屏幕底部坐标。

设计时预算小屏和大屏的可用高度，保留触摸目标与反馈空间；宽屏不无限拉开控件组。不要用裁切、缩小触摸区或滚动谜题来遮住布局问题。具体尺寸以 UI-RULES 为准；设计兼容目标不等于已完成机型验证。

### 响应式布局代码规范

适用于新建或修改的所有游戏页面与共享控件；按**可用空间**适配，不按 iPhone 型号、屏幕像素或显示倍率写分支。保留已批准的 320×160 场景坐标、锁板外观和 UI-RULES 中的控件尺寸。

1. **先算容器，再排内容。** 根层从安全区域内的尺寸扣除 54 pt footer 和左右导航 gutter，拟合出 content viewport；子页面只使用收到的 viewport 尺寸。背景可以延伸到安全区外，文字、按钮、热点及反馈保持在安全区和各自内容边界内。不要在子页面再次扣 footer 或按整块设备屏幕定位。
2. **先列不可压缩的尺寸。** 布局前预算控件本身、间距、反馈、文字最大状态和边缘留白。例如锁板键帽为 48×48 pt、间距为 8 pt；退格、Enter、Back 保留规定的触控尺寸。可用宽高任一方向不足，就换排列；不得靠 `.clipped()`、`minimumScaleFactor`、负 padding、覆盖 footer 或缩小触控区域让页面看似放得下。
3. **用容器约束选择少量排布。** 普通控件优先用 `HStack`、`VStack`、固定列 `Grid` 与 `Spacer` 表达关系；完整排布能给出可靠理想尺寸时可用 `ViewThatFits`。需要精确预算的谜题，在 `GeometryReader` 内用 viewport 宽高判断该排布是否真的容得下，选择横排、竖排或分页，而非判断 `.compact`、设备名称或只判断宽度。相同控件组在大屏设最大宽度并居中，不把固定间距拉大。
4. **图像与交互共用拟合变换。** 场景、近景或物件图按原比例 aspect-fit；从同一实际绘制区域换算物件位置、热点、拖放目标、遮罩和手势坐标。计入留白、alpha 边界及旋转后的轮廓。物件移动时更新同源命中区域，不能只移动可见图像。
5. **内容变化不改变关键控件位置。** 为反馈、最长合法输入、错误状态和已拿取状态留好空间；显示或清除反馈不移动键盘和提交按钮。文字优先在明确的物理表面内排版；空间不足时调整排布或按既有翻页规则分页，不把谜题变成滚动页面。
6. **明确支持边界。** 每个新增排布在代码审查时写清所需的最小内容宽高及放不下时采用的排布；若规定尺寸在目标 viewport 内数学上无法共存，先调整内容结构或设计，不暗中降低触控尺寸。检查最短可用高度、最窄可用宽度和宽屏，以及空白、最长内容和反馈状态；设备运行与截图是否执行仍由 UI-RULES 的测试政策决定。

## 复用机制，保留物件差异

优先复用已有 PuzzleButton、导航箭头、字体、反馈、库存、收集动效和显式 InspectionSurface。新增场景逻辑放在所属玩法模块，共享壳只负责共同布局；不把所有谜题塞进一个万能条件分支，也不为一次小改动建立一套新框架。

擦拭共享连续归一化笔画、抬指断开、局部覆盖判定及部分进度保存；石墨、镜面凝露、雨湿纸各有材质，不能共用一层平灰遮罩。线索显隐与涂层透明度分离，薄水汽不能提前泄露未擦区域的答案。完成时不清空未擦区域，不用手势次数代替覆盖。

导航保持返回链，记录发起近景的视角；打开近景后屏蔽背后房间热点。图上的对象移动或替换时，同时更新命中区域、工具落点和可访问名称。关联物件以一个共享参考画布组件管理（如 BigTopMenuDiscovery 的 320×160）；主景与近景复用组合，不独立猜测物件坐标。先核对源图／alpha 边界、旋转后轮廓与 aspect-fit 留白，再确定热点。不要留下“看得到点不到”或“点桌子却开盒”的脱节。

## 素材就是交互的一部分

先看现有批准素材和共享控件，再制作新图或预览。物件移除、拿走、开合时，背景和独立精灵必须表达同一事实；不能只改逻辑而让票仍画在旧位置。

保留高分辨率 source 与生成来源，每个 1x／2x／3x 直接从 source 导出，保留透明通道。设计板不作为运行时整张界面；文字、按钮和可互动对象独立接入。资源倍率增大不等于原图细节增加。复用现有资源导出方式，避免批量重做无关素材。

## 招牌、原料和货架的接入步骤

涉及招牌文字、成组工具素材或柜内摆放，先按 [UI 规则](../ui/UI-RULES.md#sign-lettering-ingredient-artwork-and-shelf-placement) 完成以下资料，再写场景布局：

1. 原料资产表：稳定 ID、源图、导出资源、视觉区分、透明边界与支撑锚点。禁止以通用瓶加不同名字冒充独立素材。
2. 承载面表：每个视角的招牌内框、柜格范围、层板接触线和上方净空；不要把整个场景的可用尺寸当成物件容器。
3. 放置表：ID 对应固定槽位；以可见底部对齐层板，计入 alpha 留白、aspect-fit 和旋转。热点与落点复用同一变换，拿走后的空位不重排。
4. 状态核对：招牌完整文字、柜门关闭／打开、部分拿取／全部拿取、Tools 与调香台的素材身份一致。源码审查与实际画面验证分别记录；未运行不得写已验证。

## 工作方式与交付

把规则落实到可追溯的设计约束，而不是仅声称“已遵循规范”。针对本次修改，在对应设计记录中列明相关规则、负责实现的布局／状态入口、采用的批准素材，以及尚未完成的项目。设计稿批准、代码完成、源码审查、设备画面和实际交互是不同证据；缺少素材或仍使用占位图时明确标注未完成，不能用构建通过替代。

收到实测问题先区分截图直接可见的事实、代码确认的行为和待复现的推测。修复共享问题时检查同一入口／组件的其他调用方，例如 Notes 与实体配方册；不要未经检查扩大为全游戏故障，也不要仅补当前截图而保留共用路径中的原因。规则变更在权威出处更新并清理直接冲突的旧表述，历史批准不自动覆盖最新要求。

先读取任务相关文件与已有修改；多人／多任务共享工作区时，只处理当前范围，不覆盖、清理或回滚他人的未提交工作。文档整理不混入玩法改造。

常规开发、设计、文档与 polish 的测试由用户负责。**不自动运行测试、校验脚本、验证构建、设备启动、截图或手势试验，也不为每次交付询问测试例外。** 本条执行细则唯一来源为 [测试政策](../ui/UI-RULES.md#testing-policy--user-owned-by-default)；其优先于旧计划及通用 skill 的默认验证步骤。

明确调试问题或用户要求测试时，才执行相关、串行、有界的轻量检查。需要真机时用 `mango's 17pm`，不能因不可用而自行启动模拟器。明确构建／安装授权只覆盖对应动作。

交付说明实际改变、保存兼容和未做的验证。区分“代码完成”“构建通过”“设备显示”“手势实测”“用户已验收”，不借旧测试结果给新改动背书。新偏好写回对应规则源，历史计划保留出处但不成为新任务的执行清单。
